# 入库：从收件箱文件到卡片

[English](ingest.md)

本页说明 `sb ingest` 做什么、每项检查退回什么、写入什么，以及怎样恢复。[README](../README.zh-CN.md) 里有简短版本。

## 收件箱

```sh
sb inbox list                                   # 收件箱里的每个文件，附状态和任务 id
sb inbox show "<name>" --head 60                # 一个文件的前几行
sb inbox skip "<name>" --reason "a receipt"     # 把一个文件标为不是知识
```

文件的状态是 `new`、`in_progress`、`done`、`partial`（还有卡片待定；见 `sb ingest --retry`）、`skipped` 或 `failed`。状态按内容哈希确定，所以已入库文件改名后的副本仍是 `done`。来源的文件离开收件箱后，下面两种仍留在列表里：`partial` 的来源，以及从收件箱入库、状态为 `done` 的来源。这时 `in_inbox: false`，`path` 指向 `40_Sources/` 里的副本。[Agent Skill](../skills/secondbrain/references/triage.md) 列出哪些内容应该做成卡片，哪些不应该。

## 开始处理一份来源

```sh
sb ingest <file>...                 # 一个或多个文件，位置不限
sb ingest --all                     # 收件箱里每个新的或未完成的文件
sb ingest <file> --prepare-only     # 只冻结和切块，不调用模型
sb ingest <file> --proposal-only    # 生产和复核，但不写入
sb ingest --retry <job>             # 再试一次部分完成的任务里的待定卡
sb ingest <file> --domain <slug> --pillar "<pillar>"   # 把卡片放到这里（也可加 --topic）
```

`--executor host|api` 覆盖 `[executor] default`。`--max-rounds N` 覆盖本次运行的内容返修轮数（`[review] max_repair_rounds`）。任务把这个轮数和其他设置一起保留下来（[任务保留的设置](#任务保留的设置)）。

要指定一份来源的卡片放在哪里，加 `--domain <slug>`，还可以再加 `--pillar "<pillar>"`，然后加 `--topic "<topic>"`（MCP 工具 `ingest_prepare` 接受同样三个参数）。放置位置随任务冻结，重试也沿用；`--retry` 同时带放置参数会报错。如果这份来源之前已用别的放置位置冻结，任务沿用原来的位置，`sb ingest`（或 `ingest_prepare`）会返回一条 `placement_note` 说明这一点。放置的领域排在每个块候选领域的第一位。生产者把卡片放到这里，除非卡片的主题在分类体系里已经有自己的主题（例如某个算法、某种数据结构、另一门语言）；没有这个理由却放到别处的卡片，复核者会退回。不存在的领域、支柱或主题会被拒绝，错误信息列出现有的；`--topic` 必须已经在这个支柱的 `topics` 里。没有创建主题的命令：在 `20_MOCs/_pillars/<MOC>.yaml` 里这个支柱的 `topics:` 下加上名字，或让 `sb curate` 提议。

## 各个步骤

| 步骤 | 做什么 |
|---|---|
| 冻结 | 来源字节、提取出的文本、各个块、领域目录（catalog）、完整的分类体系、每块的候选卡、复核规则和 `[ingest]` 设置都存为任务（job）的输入，并附一个哈希。没有配置转换器时，只读取 UTF-8 文本。超过 `max_source_bytes` 的来源会被拒绝。 |
| 切块 | 文本被切成精确、连续的片段，每段约 `chunk_chars` 个字符。优先在标题和空行处切，其次在句末切。 |
| 前文说明 | 来源有两块或更多时，每块都带一段说明，交代它在来源里的位置：它开头所在的各级标题、上一块的末尾、整份来源的目录（[见下](#前文说明)）。 |
| 路由 | 块里的每一段（两个空行之间的文字，连同它的标题）都在已有卡片中检索。最佳匹配所在的领域成为这个块的候选领域。每一段的前 15 张匹配卡成为它的候选卡（[见下](#候选卡)）。超过 400 字、有 7 行以上、行间没有空行的块（例如一份汇总清单）按行检索。 |
| 生产 | 生产者拿到：这个块和它的前文说明；所有领域及各自的引导问题；候选领域的完整分类体系（附每个主题的卡片数）；每一段的候选卡，以及这些卡所在主题的书架；在 API 模式下，还有同一来源前面各块已经提出的卡片：那里各块依次运行。在宿主模式下，`sb ingest` 一次发出所有块的第一轮生产任务，所以这些生产者看不到其他块的卡片。它返回卡片、提议的新主题和一张覆盖表。覆盖表的每一行说明一段文字的去向：做成了卡片；已有卡片已经全有（`same`，在 `with` 里列出那些卡的 id）；不值得保留（`out_of_scope`）；或需要新支柱或新领域（`needs_taxonomy`）。卡片可以带 `overlap_hint`，例如说它补充某张已有卡；这只是提议，程序从不据此定结局。 |
| 检查 | 答案提交时，程序先修好不用写知识文字就能改的错，再校验它（清单见下）。仍没过的卡单独退回给生产者；整块的问题退回整份答案。无效答案会被重新要一次，最多 `max_invalid_retries` 次；不占返修轮。 |
| 复核 | 复核者在另一次运行里拿到：这个块和它的前文说明；去掉生产者理由的卡片；同一来源所有其他块的卡片；每张卡要对照的已有卡片（[候选卡](#候选卡)）；分类体系。它对每张卡和每个新主题判定 `accept` 或 `revise`，并判定覆盖表是否正确，每项都附理由。`same` 覆盖行只有在它点名的已有卡片确实含有那段文字的每一点时才算对。对每张接受的卡，复核者还要判定它和库里的卡重复多少：`same`、`extends` 或 `distinct`，并在 `with` 里列出那些已有卡片（[新卡和旧卡重复多少](#新卡和旧卡重复多少)）。接受时它可以直接给机械修正，也可以写备注，每条备注带类别（[复核规则](#复核规则)）。它不会只因为另一个块讲了同一点就要求修改卡片；这由合并核对处理。如果 `depends_on` 或 `required_by` 把讲某个库、工具或语言特性的卡片，当作它所实现的概念、或另一门语言的卡片的前置，复核者会退回：这类卡片用 `similar_to` 或 `contrasts_with`。生产者和复核者都可以标出 `conflicts`，即新卡与已有卡说法不一致的地方。卡片的本质、直觉和每条易混，每一句都要有块里的原文支撑，或者只写用 `[[标题]]` 点名的那张卡里写着的内容；两样都没有的事实记为 `fact` 备注，生产者那边也是这样要求的。 |
| 返修 | 标为 `revise` 的卡片连同复核者的意见退回生产者，最多 `max_repair_rounds` 轮（默认 2 轮）。已接受的卡片保留。生产者在这里也能看到所有其他块的卡片。这一轮还会看到前几轮没有做成卡片就已了结的内容（已有卡片已经含有的段落、超出范围的段落，即 `already_settled`），不会再写一遍。如果复核者退回了一个新主题，归在它下面、已被接受的卡片会作为 `refile_cards` 退回；生产者可以用同样的 slug，把它们归到改名后的主题或已有主题下，再交复核。返修时被拆分或去掉的被退回卡片不再留作待定，由后一轮的覆盖判定决定。返修轮的复核者逐条核上一轮的问题改好没有（[复核规则](#复核规则)）。 |
| 闸门 | 只有另一次运行中的复核者接受了的卡片才会写入。带阻塞类备注的接受按退回算。最后一轮之后仍被退回的卡片成为待定，附上理由。返修后仍归在被退回的新主题下的卡片也成为待定。 |
| 分流 | 程序按复核者判定的重复程度分流接受的卡：`same` 的卡不写入，列进 `duplicates`；`extends` 的卡进它所补充的已有卡的补丁集；`distinct` 的卡进合并核对。 |
| 合并核对 | 由一个复核者把这份来源的卡片放在一起判断：`distinct` 的卡互相比较、新主题、每张被本来源的卡补充的已有卡的补丁（[见下](#合并核对)）。`distinct` 的卡来自两块或更多时，或有卡在等它的补丁时，才运行。 |
| 拆卡 | 补丁会让已有卡超过 12 条命题或 8 组问答时，新卡在拆槽里改写成一张回答更窄问题的卡，再经复核（[见下](#新卡补进已有卡)）。 |
| 画图 | 已接受的卡片进入画图步骤（[diagrams.zh-CN.md](diagrams.zh-CN.md)）。 |
| 写入 | 一个事务（见下文）。 |
| git 提交 | 设了 `[git] commit = true` 时，工具提交写过的路径。提交失败会记录下来，但不撤销写入。 |

### 检查会退回什么

- `source_quotes` 里的引文不是块中的逐字原文（错误信息会给出最接近的段落）；
- 分类体系里没有的领域、支柱或主题，除非它是已有支柱下一个合法的新主题提议；
- 与已有主题重复或只是改名的新主题、超过每份来源允许数量的新主题，或没有卡片使用的提议主题；
- 卡片所在领域不能用的关系类型（领域目录的 `relation_types` 对所有领域开放；只列在 `domain_relations.<domain>` 下的类型只对那个领域开放）、目标领域不能用其反向类型的链接，或既不是已有卡片、也不是本来源卡片的关系目标；
- 同一对卡片之间的两条关系（程序补写的反向关系也算在内）；
- 方向相反的两条关系：一张卡片对同一目标既有某个类型又有它的反向类型，或两张卡片互相声称同一类型；
- 有 `contrasts_with` 关系、却没在 `confusions` 里写出区别的卡片；
- 重复的 slug、生成的卡片 id 已被已有卡片占用的 slug（已有 `kc_spacing-effect` 时的 `spacing-effect`）、不能用作文件名的标题，或已有卡片已经在用的标题；
- 少于两组或多于四组问答，或问答里含有 `::`；
- 写进正文的卡片 id（卡片之间用 `[[Title]]` 互相引用）；
- 覆盖表里缺少的卡片，或引文不在块中的覆盖表行；
- 答案里任何一处 JSON 类型不对的值，例如名字该是字符串的地方给了对象（[见下](#形状不对的答案)）。

两个标题或两个主题名，如果按[怎样算同一段文字](#怎样算同一段文字)判为同一段文字，就算重名。

### 检查之前程序先修什么

检查之前，答案里那些不用写任何知识文字就能改好的错，程序按一张固定的规则表、依下面的次序先修好，每处都记下来（任务结果的 `program_repairs`；复核者的包里也给出）。每个产卡的角色都在同一处修：块的答案用全部规则；拆出的卡只用 `title`、`card_id` 和 `quote`，它的关系留给它自己的检查（那项检查要求它用指定类型链接它所细化的卡）：

| 规则 | 修法 |
|---|---|
| `title` | 标题里不许用的字符写成全角（`/` 写成 `／`）；答案里指向这张卡的链接跟着改 |
| `card_id` | 正文里用 id 指称的卡（`kc_lantern-queue`），id 是已有卡或本答案里的卡时，改用 `[[标题]]` |
| `quote` | 引文去掉 `**`、`__` 和空白后是块里的一段、在块里只出现一次、且至少 8 个字符时，换成块里那段原文；不做别的匹配 |
| `relation_target` | 指向既不是已有卡、也不是本来源卡片的关系，删掉 |
| `relation_pair` | 同一对卡之间两条以上的关系（程序补写的反向关系也算），只留领域目录里类型次序最靠前的那条 |
| `relation_direction` | 方向相反的两条关系删一条：同一张卡上，删类型次序靠后的那条；两张卡之间，删 slug 靠后的那张卡上的那条 |

本质、命题、直觉、易混和问答在修前修后要比对，比之前两边都先写成同一种写法（指称卡片的 id 写成它的 `[[标题]]`，该写全角的标题写成全角），所以一张卡在一处用 `[[标题]]`、在另一处用 id 指称同一张卡时，会被修好，不会被当成改了知识文字。修复在别处改动了它们，就是程序的错：答案被退回并计数，这个错列给你看（[形状不对的答案](#形状不对的答案)）。API 模式和 `sb job submit` 用同一种读法：先按原样读 JSON；不行就去掉整份答案外面的一层 Markdown 代码围栏再读（```` ```json … ``` ````，`fence`）；还不行、而 JSON 对象前后有别的文字时，只读这个对象（`around`）。运行记下用了哪种，`program_repairs` 也列出来。别的都不放宽：用字面的 `\n` 当换行写的答案仍然不是 JSON。

### 没过检查的卡单独退回

检查查出的问题只涉及部分卡时，答案只为这几张卡退回，通过的卡留下。不论涉及几张卡，这次退回在这个槽位的 `max_invalid_retries` 里只算一次；计数存在任务里，任务再跑时接着计。下一次要答案时，把没过的卡按上次给的原样、连同它们的错误行给出（包里的 `fix`：`cards`、`problems`、`kept`），只要这几张卡；交回的卡和留下的卡合在一起，整份再校验。槽位的最后一份答案里仍有没过的卡时，通过的卡照常进复核，没过的卡连同错误行和卡的内容等你处理（`pending`，带 `card`；它们的覆盖表行、以及只有它们用的新主题一并去掉，记为 `held_back`）。整块的问题（覆盖表、新主题）仍然退回整份答案。宿主模式也一样：`sb job submit` 同样先修、留下通过的卡、按卡退回，子代理只交回没过的那几张卡。

## 候选卡

凡是要把新卡和库里的卡比较的角色，都从同一个函数拿已有卡片：生产者、块复核者、合并核对和拆槽。候选卡只是要看的卡。新卡是否重复它，由复核者判断，从不按分数定。

每一行候选卡都在 `via` 里写明它的来路：

| `via` | 这张卡 |
|---|---|
| `named` | 生产者点名的卡：关系目标、冲突对象、`overlap_hint` 里的卡，或 `same` 覆盖行里的卡。 |
| `written` | 重试时：这份来源以前的任务写入的卡。 |
| `words` | 检索命中的卡：在整个知识库上做词面检索（BM25），取前 15 张。 |
| `hop` | 检索命中的卡所链接的卡。默认不开（`candidates_hop = 0`）。 |
| `shelf` | 归在同一主题下的卡，每个主题最多 25 张。 |

一张卡按四种视图之一给出，后一种包含前一种的全部内容：

| 视图 | 包含 |
|---|---|
| `title` | id 和标题 |
| `brief` | 再加领域、支柱、主题和本质（截到 300 字） |
| `full` | 再加每条命题，以及每组问答连同答案 |
| `body` | 整张卡的正文（只有 `sb export` 用） |

命题没有按 `P1`、`P2`……编号，或问答里没有 `::` 的卡，在 `full` 视图下给出正文开头一段，并标 `format: legacy`。

**一个预算。** 一个包里，检索到的卡的视图最多占 `candidates_chars` 个字符（40,000）。每张已有卡只出现一次，不管它挨着几张新卡。装包顺序按第一张表：点名卡、已写入的卡、检索命中的卡、一跳的卡、书架。点名卡保持原来的视图，不计入预算。其余的卡超出预算时，从视图最详细的卡里排名最低的那张开始，每次降一级（`full` 降到 `brief`，`brief` 降到 `title`），一次一张，所以排名靠前的卡保留得最多。所有卡都只剩 `title` 还超出时，去掉排名最低的标题。所以书架上的标题总是比检索命中的卡先去掉。点名卡本身就超过预算的两倍时，这一块对半切开，重新生产。

各角色拿到什么：

| 角色 | 卡片 | 视图 |
|---|---|---|
| 生产者 | 每一段检索命中的 15 张卡；这些卡所在主题的书架，按各主题最好的命中排序，每个书架里排名靠前的卡在前 | 命中的卡 `brief`，书架 `title` |
| 块复核者 | 每张新卡：生产者点名的已有卡、它检索命中的 15 张卡、它所在主题的书架；重试时，还有这份来源以前的任务写入的卡；`#coverage` 下是覆盖行点名的卡 | 点名卡 `full`，从不降级；已写入的卡 `full`；命中的卡 `brief`（`review_words_view`）；书架 `title` |
| 合并核对 | 每张卡检索命中的 15 张卡，只用来补链接；每张卡按 id 列出，最接近的在前 | `brief`，在预算内降级 |
| 拆槽 | 新卡要缩窄的那张已有卡 | 生产者看 `body`，它的复核者看 `full` |

为什么取这些值：

- **各角色都取 15 张，不按库的规模分档。** 在 197 到 8,738 张卡的库上，每一档都是取到 15 张之后，再多取 5 张，找回的真重复都多不到 2 个百分点。取 15 张时，检索找回了 95.9% 的真重复。
- **不开第二路。** 检索命中卡所链接的卡，并没有比多检索几张找到更多重复。
- **在整个知识库上检索。** 只在相关领域里检索，找回的重复少 0.68 个百分点，读的量也没有减少。前 15 张命中卡里约 12% 落在相关领域之外，其中有真重复。
- **长清单按行检索。** 一章汇总的各条目之间没有空行。整块作一次查询时，生产者为各条目点名的卡，只有 52% 出现在前 5 张命中里；每行作一次查询时，全部都在。
- **40,000 字。** 预算为 20,000 字时，复核者检出的注入错误少 3 个百分点；80,000 字时并不更多。
- **点名卡给全文。** 生产者说某张已有卡已经有这段内容时，复核者要拿那张卡来核。以前在 11 个真实任务里，生产者点名了 71 张次旧卡，复核者只看到 6 张次。
- **复核者看检索命中的卡用 `brief`。** Opus 复核者用 `brief` 比用 `full` 检出的注入错误少约 1 个百分点（80 处里 62 对 63），读的量少约 12%。DeepSeek Flash 复核者少约 6 个百分点。用 Flash 一档的模型做复核时，设 `review_words_view = "full"`。
- **书架。** 书架让人看到一个主题里已经有什么，便于把卡归到这里，也便于发现同一主题下的重复。每个主题约多 25 个标题。它的效果没有测过；因为便宜，默认打开。

## 新卡和旧卡重复多少

凡是判断重复的地方，都用同一把三档尺。要判断重复的每份提示词，都写着同一段定义：

- `same`：这张卡没有 `with` 里那些卡没有的内容。它的知识可能分散在其中几张里。
- `extends`：这张卡讲的是 `with` 里那一张卡的同一个对象或问题，或它的一个子问题，多出细节、例子、情形或某个子问题的答案。并进那张卡后，那张卡仍只回答一个问题。
- `distinct`：这张卡讲的是另一个对象或另一个问题。并进 `with` 里的卡后，那张卡就不再只回答一个问题。

同一问题的更多例子或情形，不算一个独立的单元：它们是 `extends`。

**每个值只有一个终判者。** 决定写入什么的每个值，都只由一个角色给出：

| 值 | 终判者 |
|---|---|
| 卡的判定（`accept` 或 `revise`）和它对库里的卡的重复程度（重试时也对这份来源已写入的卡） | 块复核者 |
| `distinct` 的卡对本来源其他卡的重复程度；一个新主题与另一个新主题是否相同；已有卡的补丁；异议 | 合并核对 |
| 拆出的卡的判定，以及它没有重述它的已有卡 | 拆槽的复核者 |
| 补丁补完是否超过 12 条命题、8 组问答 | 程序 |

生产者只提议。接受的卡最后怎样：

| 档位 | 对库里的卡（块复核者） | 对本来源的卡（合并核对） |
|---|---|---|
| `same` | 不写入；列进 `duplicates` | 不写入；它的链接改指 `with` 里的第一张卡 |
| `extends` | 补进那张已有卡（[见下](#新卡补进已有卡)） | 它多出的内容补进 `with` 里那张卡 |
| `distinct` | 进合并核对 | 写入，并补上链接 |

**判定记录。** 每个值都追加到任务的判定记录里（任务结果的 `decision_record`），带上给出它的角色、槽位和运行。只有终判者能再给一次值，而且要有任务里看得到的理由：一轮返修、改归另一个主题，或一条异议。除此之外的第二个值都算错误。写入步骤只从这份记录读卡片的位置、关系和结局；任务结果的 `outcomes` 给出每张接受的卡的结局。以前，同一种重复有五种说法，在不同步骤可能有不同结局，后一步还可能不留痕迹地改掉前一步的值。

## 新卡补进已有卡

复核者判为 `extends` 某张已有卡的卡，不再作为新卡写入。它多出的内容补进那张已有卡；每张已有卡由合并核对合成一份补丁：

- 新命题接着往下编号；
- 一条更完整的说法可以按编号替换一条命题；
- 新问答排在旧问答后面；旧的一组问答可以换成更完整或更清楚的一组（`flashcard_replace`，按编号 `Q1`、`Q2`……），新答案保留旧答案的每个事实；复习排程按整张卡记，所以这张卡的复习进度不丢（只有那个问题自己的单条记录对不上，见[复习记录](review-registry.zh-CN.md)）；
- 来源段落加进 `sources`，并写明它支持哪几条命题；
- 新卡的关系移到那张已有卡上。

已有卡的其余字节都不变。会改动其他内容的补丁，程序拒绝。

例子：库里有一张卡“灯笼队列”，有 P1 到 P4 和三组问答。一份新来源里有一张卡“灯笼出队顺序”：灯笼按点亮的先后出队，并附一个例子。复核者判它 `extends`“灯笼队列”。合并核对合成补丁：那个例子成为 P5，再加一组问答问出队顺序。“灯笼出队顺序”不写入，指向它的链接改指“灯笼队列”。

**太长了：拆槽。** 补丁会让已有卡超过 12 条命题或 8 组问答时，已有卡不动（补丁里换问答的也不换：任务结果在 `replacements_not_made` 里列出）。补充它的每张新卡各进一个拆槽（`sp01`、`sp02`……），只带这张卡自己多出的内容：补丁里来自它的命题、问答、替换和 `already` 行。生产者在那里把它改写成一张更窄的卡：只含已有卡没有的内容（它在某种情形下怎样表现，或一个完整的例子），并用 `part_of` 或 `example_of` 关系连到已有卡。一张卡的命题如果已有卡全都说过（全在 `already` 里），就不开拆槽：它别的什么都不带时，不写入，指向它的链接改指那张已有卡；它还带着问答时，这些问答作为一份单独的补丁补进已有卡，补进后会超过 8 组问答时，这份补丁被扣下（这张卡写在已有卡旁边、标为待复核，并列进 `patches_held`）。拆出的卡若有一条命题和已有卡的某条是同一段文字，程序退回重问。同一张已有卡的两张拆卡说了同一点时，后一个拆槽的卡退回重问。程序不删任何内容。另一次运行里的拆槽复核者核对：这张卡忠实于原文、不看来源也读得懂、是一个单元。它还要在 `matches` 里为这张卡的每条命题写明：已有卡哪一条用任何说法说过同一件事，没有就写 `null`。复核者接受了一张有对应条目的卡时，程序把卡退回，去掉那一条重写。被退回的拆卡在返修轮（`sp01.r1`……）里重写，最多 `max_repair_rounds` 轮；之后仍不过就留作待定。同一份来源里，被别的卡并入的那张卡会超限时也一样：补充它的那张卡进拆槽，被补充的那张保持原样。

**改为写在旧卡旁边。** 下面几种情况下，新卡写在它补充的已有卡旁边，带 `status: needs-review` 和 `review_reason: [possible_repeat]`：

- 已有卡不是 sb 的格式（命题没有按 `- P1.`、`- P2.`……编号，或问答里有一行没有 `::`），或这张卡已经不在了；
- 在合并核对的最后一份答案里，它的补丁仍没过程序检查（[见下](#合并核对)），或合并核对被放弃了；
- `[ingest] merge_into_existing` 设为 `false`。

任务结果在 `needs_review` 里列出这张卡，`not_merged` 写明原因。

补丁会改动已有卡的正文，所以它上面未解决的冲突会按新正文重新记一次：合并不等于冲突已解决。

为什么：以前这种卡写在已有卡旁边、标待复核，由你手工合并两张卡。在一次 72 张接受卡的实验里，新规则把 40 张补进了已有卡，拆出 11 张，没有留给人复核的；旧规则留下 53 张待复核。后来的一次实验里，每个拆槽都拿到整份补丁：两个拆槽写出了同一张更窄的卡，另外两张卡多出的内容丢了。所以现在每个拆槽只拿它自己那张卡多出的内容。在一个大型知识库的副本上，96.8% 的卡（8,738 张里 8,456 张）是 sb 的格式，可以接受补丁。

## 合并核对

每个块都单独生产、单独复核。所以两个块可能各写一张讲同一点的卡，不同块里本该相连的卡片没有链接，两个块也可能各提一个讲同一主题的新主题。所有块都了结之后、画图之前，还有一次复核者交接（`chunk: xc01`，`step: source_check`），把这些放在一起判断。块复核者判为 `distinct` 的卡来自两块或更多时，或有卡在等它的补丁时，才运行。

它读：

- 判定集：块复核者判为 `distinct` 的每张卡，按领域、支柱和主题排序，带它的关系、本来源里链接它的卡，以及它的复核备注（写成“[类别] 内容”）；
- 补丁集：被本来源的卡补充的每张已有卡（`full` 视图），以及补充它的那些卡；
- 这份来源的新主题，附每个主题下的卡片数；
- 每张卡的候选卡，只用来补链接：每张卡按 id 列出，最接近的在前；每张已有卡只在一张表里出现一次，总量在 `candidates_chars` 之内；
- 前文说明打开时，来源的目录。

它不读块的原文：内容已由块复核者核过。冻结的任务包在 `packing` 里报告自己的大小。

**判定集。** 每张卡给出它对本来源其他卡的重复程度：

- `extends`，`with` 指出本来源的一张卡：它多出的内容逐字抄进 `carry`（`{"propositions": [...], "flashcards": [{"q": ..., "a": ...}]}`），连同它的原文位置，补到那张卡上。`replace`（`[{"proposition": "P2", "by": "<这张卡的命题，逐字>"}]`）用一条更完整的命题替换那张卡的某一条，`flashcard_replace`（`[{"flashcard": "Q1", "q": ..., "a": ...}]`）用更完整或更清楚的一组问答替换那张卡的某一组。这张卡不写入。指向它的链接（关系里的，以及正文里的 `[[Title]]`，包括带 `#标题` 或 `|别名` 的写法）都改指 `with` 里那张卡，它自己的链接也移过去；如果那张卡已经链接了同一目标，或者移过去会造成自己链接自己，就不移。
- `same`：什么都不抄。这张卡不写入，它的链接改指 `with` 里的第一张卡。
- `distinct`：这张卡写入。它可以在 `links` 里补上应有而还没有的关系：指向本来源的其他卡（用 slug），或指向它的候选卡（用 id）。

**补丁集。** 每张已有卡，合并核对合成一份补丁（`{"target", "propositions", "flashcards", "replace", "flashcard_replace"}`），除换问答外，每一项都从补充它的那些卡里逐字抄。换问答（`{"flashcard": "Q2", "q": ..., "a": ...}`）让已有卡的某一组问答更完整或更清楚：新答案保留旧答案的每个事实（做不到时，合并核对改为新加一组），来源说旧答案错了时，那是交给你的冲突，不换。某张卡没有可补的内容，或它要补的内容其实回答的是另一个问题时，合并核对把它列进 `disputes` 并写明理由。这张卡退回它的块复核者重判（槽位 `xr<n>-<slug>`，步骤 `dispute`）。然后合并核对作为新的一轮重跑（`xc01.r1`……），这一轮整体取代上一轮。`max_repair_rounds` 用完后仍有异议的卡留作待定。异议卡的重判答案一再没过程序校验（`max_invalid_retries`）时，这张卡也留作待定，并写明异议和最后一次校验消息。

**程序核对答案的哪些地方：**

- **每条命题、每组问答都有交代。** `extends` 的卡、以及补充已有卡的那些卡，每条命题都要么抄过去，要么用在 `replace` 里，要么列进 `already` 并写明已有卡哪一条已经说了它（`{"text": "<逐字>", "as": "P3"}`）。它们的每组问答都要么抄过去，要么用 `flashcard_replace` 换进去（新问题就是它的问题），要么列进 `already` 并写明已有卡哪一组已经问了它（`{"text": "<它的问题，逐字>", "as": "Q2"}`）。漏了一条的答案退回，并写明漏的是哪一条。加上写前的检查（见下），并进别的卡的卡，没有一条会不声不响地丢下。
- **同一点不说两遍。** 补丁里，以及并进本来源某张卡的 `carry` 里，每条抄过去的命题和问题、每条替换，都和它要进的那张卡比较，也和一起抄过去的其他条目比较。补丁里与已有卡某一条逐字相同（不计空白）的条目，一律退回：把那一条列进 `already`。只是看起来相同的（[怎样算同一段文字](#怎样算同一段文字)），以及说法很接近的，也退回，除非答案在 `differs`（`{"text": ..., "from": ..., "reason": ...}`）里列出这一对，说明为什么是另一个要点。`from` 指出那张卡的一条命题（`P3`）或一组问答（`Q2`），或同一份补丁里的另一条。退回的信息写出两边各是哪一条。一组问答的问题与那张卡（或一起抄过去的另一组问答）的问题逐字相同、答案却不同时，也退回，并写出两边的答案；可以用 `differs` 把两组都留下。换问答要指出卡里有的一组，每组最多换一次；新的一组照同样的规矩和卡里别的问答、一起抄过去的问答、别的换问答比较，问题和答案都与其中一组相同的，退回。程序从不因为“看起来相同”就去掉条目，而是退回去问。它自己只去掉重复的条目：逐字相同（不计空白）的命题，或问题和答案都逐字相同的问答；并进本来源某张卡时重复了那张卡的，或同一条抄了两次的。写入接受补丁或 `carry` 的卡之前，程序核对其中每条命题、每组问答、每条替换、每组换进去的问答都在卡里；有一条不在，任务就停下并写明是哪一条，什么都不写。这项检查长在把补丁写进已有卡、把 `carry` 并进本来源的卡的那两个函数里，所以任何写卡的路都绕不过它。合并核对还被要求把每条抄过去的命题逐条对照那张卡的命题：卡里有一条概括了它所讲的那组名字或术语时，把它放进 `replace` 换掉那一条，而不是加在旁边（这是提示词里的要求，程序不核）。
- **按问题判，不按长短判。** 合并核对不能为了不超限而裁掉补丁。超过 12 条命题或 8 组问答时，由程序把卡送进拆槽。
- **链接：** 类型对两边的领域都开放，同一对卡片只有一条关系，不指向不写入的卡。没有任何关系的卡（`isolated: true`）必须加上链接、被别的卡链接，或在 `alone` 里说明为什么单独存在。
- **新主题：** 每个新主题判为 `distinct`，或 `same` 加另一个新主题的 id。后一种情况下，它下面的卡片改归到那个主题（它的领域、支柱和主题），这个主题不加入分类体系。任务指定了放置位置（`--domain`）时，保留放置位置上的那个主题。

没过这些检查的答案退回合并核对，最多 `max_invalid_retries` 次。被退回的每份答案都列在任务结果的 `source_check_refusals` 里（槽位、运行和退回信息）。

合并核对能给的最后一份答案，按补丁逐张处理。只有部分补丁、或部分卡并进本来源某张卡的 `carry` 没过检查时，其余照样落下。没过的那张已有卡什么都不补：补充它的卡写在它旁边，标为待复核；任务结果的 `patches_held` 列出这张已有卡、补充它的卡和查出的问题。`carry` 被扣下的卡不并：它作为一张独立的卡写入，标为待复核，`patches_held` 里列出它并标 `carry: true`。以传输错误结束的运行不算一份答案，不计入“最后一份”。最后一份答案在别处也有问题时，整份退回，核对自动跳过。宿主模式也一样：子代理交回、被 `sb job submit` 拒收的答案，和 API 模式的答案一样计数；核对放弃后，它的运行随之关闭。子代理一直交不回答案时，运行 `sb job skip-source-check <job> --reason "<why>"`。被拒的答案和放弃的运行合计达到 `max_invalid_retries` + 1 次（默认 3 次）之后才能用；次数不够时，它会拒绝并说明目前有几次。它放弃未完成的运行并记下跳过。之后卡片按各块复核后的样子写入，不做跨块的合并或链接；补丁集里的每张卡都写在它的已有卡旁边，标为待复核。

为什么要这些检查：一次实验里，打补丁之后，41 张合成的已有卡里有 14 张、8 张重放的已有卡里有 7 张把同一点说了两遍；在补丁规则之前，20 次合并里有 3 次这样。另一次补丁会超限的实验里，合并核对把 20 份补丁里的 8 份裁到正好卡在上限，其中 5 份丢了一条命题。第三次实验里，只因一份补丁里有一组问答和已有卡的一组问答很接近，整次核对被跳过，补充 4 张已有卡的 7 张卡全写在了已有卡旁边。现在只扣下补丁没过的那张卡。

**重试时**，这份来源以前的任务写入的卡是块复核者的候选卡（`via: written`），复核者用同一把尺把每张重试卡和它们比较。没有新内容的重试卡判为 `same`，不写入；只是补充某张已写入的卡的，判为 `extends`，补进那张卡。合并核对不判已写入的卡。

已知限制：程序能发现同一段文字和说法很接近的文字，但发现不了每一处换了说法的重述。拆出的卡靠拆槽复核者的 `matches` 来查：一次实验里，23 张拆出的卡有 1 张换了说法重述已有卡的命题（另有 2 张出自拿到整份补丁的拆槽，这一点已经修了）。补丁靠合并核对逐条对照；你复习那张卡时，仍可能发现换了说法的重述。

## 前文说明

块不重叠，每块单独做成卡片。所以开头是“上面三类”的块，或在上两级标题下面的块，读的时候缺了它所指的内容。让文字重叠，又会让同一段归两个块管，同一张卡可能写两次。所以每块都带一段说明 `context_note`，由程序从来源的结构里取。总长不超过 `[ingest] context_note_chars`（2,000 字），按这个顺序装：

1. 这块开头所在的各级标题（最多 200 字）；
2. 上一块最后一两段（最多 600 字，按整段取，放不下就在某句开头处截断）；
3. 整份来源三级以内的目录，标出这块所在的位置（用剩下的预算；再放不下，只留标记前后的几行）。

生产者、块复核者和拆槽都拿到这段说明，并标明“只供理解：不可引用，不算覆盖”。引文仍只对照块本身核对，所以从说明里摘的引文会被拒绝。合并核对拿到一份来源目录。只有一块的来源不加说明。

`[ingest] context_note` 决定说明里有什么：

| 值 | 说明 |
|---|---|
| `off` | 不加说明 |
| `program`（默认） | 上面那段程序取的说明；不调用模型 |
| `summary` | 再加：第一块之后的每块，各做一次便宜的生产者调用（槽位 `nt-<chunk>`），说明前面讲了什么、本块的指代指向什么，最多 300 字 |
| `concepts` | 再加：整份来源做一次生产者调用（槽位 `nt-concepts`），列出它的概念和讲各概念的块，在说明里最多占 600 字 |

模型写的说明一再没过校验时就放弃，这块仍用程序的说明。宿主模式下，这些调用排在等它们的块之前发出。

为什么默认用 `program`：一次实验里，各组在块开头的卡都没有读不懂的（171 张里 0 张），所以实验分不出哪一组更好。程序的说明没有增加跨块边界的重复（8 对，不加说明是 10 对）。模型摘要每块多一次调用，没有显出好处。

## 复核规则

**两个额度。** `[review] max_repair_rounds`（2）数内容返修轮：复核者附理由退回一张卡。`[review] max_invalid_retries`（2）数答案没过程序校验、重新要答案的次数，按槽位计。两个额度分开计，每个调模型的角色都是这样：块的生产者和复核者、合并核对、异议后的重判、拆出卡的生产者和复核者、模型写的说明。计数存在任务状态里，任务再跑时接着计：一次 `sb job advance` 最多问 `max_invalid_retries` + 1 次，之后不再问；宿主模式下子代理交回、被 `sb job submit` 拒收的答案也这样计（文件不是 JSON、JSON 不是对象，都算），用 `sb job abandon` 放弃的运行也算，这个槽位放弃后，它的运行随之关闭。每种调模型的任务都在同一个闸口这样计：录入、导出，以及分类、整理、移卡、建领域任务的复核者和生产者；后几种额度用完时，任务停下等你处理（`escalation_required`）。用完后，块的卡、拆出的卡或异议卡留作待定并写明理由（次数和最后一次校验消息）；合并核对跳过，模型写的说明放弃。图的答案没过校验时，在它的重写槽里再问一次。以前一个额度两样都算，一份格式不对的答案就会用掉这个块唯一的一轮返修。每个角色的返修额度也在同一张角色表里，还剩不剩一轮由同一个函数判定：块、异议后合并核对的下一轮、拆槽、导出的单元、维护类任务都是这样。

**机械修正**（`[review] amend`，默认打开）。接受一张卡时，复核者可以在 `amend` 里直接修正不需要新知识文字的问题，不必退回：

- `add_relation`、`retype_relation`、`remove_relation`：补上缺的关系，改正类型或方向错的关系，删掉错的关系；
- `refile`：把卡改归到分类体系里已有的主题下；
- `drop_flashcard`：删掉块里没有依据的一组问答（至少留两组）。

程序照改，只核对结果是否合法：类型对两边都开放，主题在分类体系里，至少留两组问答，`extends` 的卡仍链接它的已有卡。不合法的修正把这次接受变成普通的退回。任务结果在 `amended` 里列出每条修正，附改前和改后；合并核对也看得到它们。

**返修轮的聚焦复核**（`[review] focused_review`，默认打开）。返修轮的复核者拿到上一轮的问题（`previous_findings`），逐条说改好没有。只有问题没改好，或有阻塞类问题（见下）时，才退回卡片。别的问题写成 `minor` 备注。

**备注带类别。** 复核者写的每条备注都是 `{"category": "<类别>", "text": "<什么问题、在哪里>"}`，类别是下面五种之一：

| 类别 | 含义 |
|---|---|
| `fact` | 说法有错：块（导出文章时是所引的卡）与它矛盾，或没有这样说 |
| `unreadable` | 不看来源就读不懂：它指向来源（“上面的例子”），或漏掉了它所依赖的内容 |
| `quote` | 引文不是块里的逐字原文，或引了一张卡却说了那张卡没说的话 |
| `not_a_unit` | 不是一个可回忆的单元：一张卡里有两个独立的想法，或是一个独立不成立的片段 |
| `minor` | 措辞、风格，或可以更好、但没有错的地方 |

每条命题都要单独看也对。一条命题单独读时，如果说得比它所依据的原文多（漏了原文给出的某个条件、限制或情形）、说错了，或读不懂，就是 `fact`（读不懂时是 `unreadable`），这张卡要退回修改。卡的本质或某组问答里还写着那个条件，不能作为把这条备注定为 `minor` 的理由。在一次注入错误实验的重放里，复核者就是因此把漏掉的条件记成了 `minor`；判官认为这样的 10 张卡里有 8 张本该退回。

前四类是阻塞类。复核者接受一张卡、却写了阻塞类备注时，程序把这次接受改成退回，退回理由就是那条备注。这次退回和别的退回一样占一轮内容返修。返修轮用完后，这张卡留作待定，理由就是那条备注。只有 `minor` 备注不改变判定。拆槽的复核者和 `sb export` 的复核者也照这条规则。旧格式的备注（一个普通字符串），或类别不在这五种里的备注，会被拒绝并重新要答案。

任务结果有两张单，`sb job show <job>` 两张都显示：

- `notes_turned`：程序改成退回的每次接受：块、槽位、第几轮（0 是第一次复核，n 是第 n 轮返修）、卡片、类别和备注；
- `review_notes`：每条备注，附类别。

为什么：两次实验里，复核者都在备注里写准了真问题，却照样接受了卡片：一次是 6 个真问题里的 3 个，另一次是 36 处注入的错误。错卡照样写进了库。现在由程序按备注处理，不多调用模型。

默认值来自一次实验：返修 1、2、3 轮，聚焦复核和机械修正分别开和关。进了复核的块都在 1 轮返修之内了结。两个开关都开时，写入的 225 张卡里有 6 张（2.7%）有真问题；7 条机械修正里错了 1 条（关系类型写错）。

## 形状不对的答案

每个角色的每份模型答案，都先按要它时给的 JSON schema 检查。JSON 类型不对的值（名字给了对象、链接给了字符串、schema 不允许的地方给了 null）会按名字指出并拒绝，例如 `cards[0].links[0] must be an object, not str`。然后在 `max_invalid_retries` 之内重新要答案。检查代码内部出的错，也变成指名的拒绝。所以错的答案从不会让 `sb ingest` 停下；以前有些会以 `TypeError` 或 `AttributeError` 停掉整次运行，并让它一直挂着。读答案、查答案时出的其他任何错，在每种任务、每个角色里都过同一个闸口：答案被退回，计入这个槽位的额度，额度用完时宿主的运行被关闭；这个错是程序的、不是答案的，记在运行和任务里，`sb status --owner-items` 列出它（`kind: program_error`）。

入库的答案先按原样读 JSON，不行就去掉外面一层代码围栏，还不行、而前后有别的文字时只读其中的 JSON 对象；API 与宿主模式一样（[见上](#检查之前程序先修什么)）。不是 JSON 的答案算无效，重新要答案。只有 `sb export` 会读答案里没转义的 TeX 反斜杠（[export.zh-CN.md](export.zh-CN.md)），宿主模式也一样。

## 怎样算同一段文字

标题、新主题名、抄过去的条目和拆出的卡，都用同一个检查比较。两段文字只在大小写、全角半角、空白和一张封闭的符号表上不同时，算同一段文字。这张表是：句读标点 `, . ; : ? !`（连同对应的中文标点，以及顿号）、引号、省略号和破折号。其余字符都算数：括号、`# % & * @ \ _ ^ ~ + = < > | / -`、数字和字母。所以“If a < b”和“If a > b”是不同的文字，“5%”和“5”、“C#”和“C”、“x_1”和“x1”也都不同。

有两种例外，表里的符号也留下：夹在两个数字之间的（3.5、3:2），以及紧跟在数字或单字母名字后面的英文 `!` 或 `'`（n!、f'）。公式（`$...$`、`$$...$$`）和行内代码按原样比较，只把连续的空白算作一个。

这个检查判出“相同”，只让答案退回重问，或给出提示；程序从不因此删掉文字。检查时会忽略一些字符，而其中有的会改变意思：“1 KB”和“1 Kb”、“10³”和“103”都可能判成相同。所以程序自己只去掉逐字相同（不计空白）的两条，其余一律退回去问。判成相同可能丢掉一个要点；判成不同，最多留下一处重复。所以拿不准时，这个检查判“不同”。

## 写入哪些内容

在一个事务里写入：

- 每张已接受的卡片，存为 `10_Knowledge/<domain>/<title>.md`，由程序根据复核过的字段生成。下面两种卡写成 `status: needs-review`，原因记在 `review_reason`：生产者标明来源不清、复核者接受了的卡（`source_unclear`）；补充某张已有卡、而那张卡接不了补丁的卡（`possible_repeat`）。这类卡在结果的 `needs_review` 里列出；这个状态改掉之前，复习队列不会把它当新卡排入。`sb status` 统计这类卡片（`needs_review`），`sb status --needs-review` 逐张列出，`HOME.md` 在「现在做什么」下给出数量；
- 新卡补充的已有卡的补丁：命题、问答、一项来源和关系，卡里别的内容都不动；
- 已有卡片上的反向关系，写进 front matter 和相关小节（卡片其余部分不变）；
- 已接受的新主题，写进分类体系文件；
- 来源副本，存为 `40_Sources/<first 16 hex of sha256>/<file name>`；
- `_data/manifest.jsonl`、收件箱登记表和 `_data/notes_registry.json`；
- 发现的冲突，追加到 `_data/secondbrain/conflicts.jsonl`；
- 受影响领域的地图页（MOC）和首页 `HOME.md`；
- 设了 `after_ingest = "move"` 时，从收件箱删除这个文件（它的字节已在来源副本里）。

卡片正文里的公式由代码放进 `$` 之间，代码也给裸写的宏名补上反斜杠（`alpha` 写成 `\alpha`）。关系符号的名字被当作函数名、后面紧跟 `(` 时，写成算子名：`sim(q, d)` 写成 `\operatorname{sim}(q, d)`，不写成关系符号 `\sim`；`X \sim p` 保持原样。二元运算符后面跟括号时仍是运算符：`w_i times(x_i + b_i)` 写成 `w_i \times(x_i + b_i)`。`softmax`、`argmax`、`argmin`、`sigmoid` 和 `relu` 一律写成算子名。

指向被复核者判为 `same` 的卡片的关系，改为指向它所重复的那张已有卡片。指向已补进某张已有卡的卡片的关系，改指那张已有卡；指向在拆槽里改写过的卡片的关系，改指拆出的卡。写不进去的关系在结果的 `skipped_relations` 里列出，原因是下面两种之一：

- `target card was not written`：目标卡还在待定。这条关系会带到重试子任务；子任务写入目标卡时补上这条关系，并在先前那张卡上加反向链接。
- `target card was dropped in review; add the link by hand if it still matters`：这条关系不再带下去。

在重试子任务里，每条带过来的关系都只有一种结果。写入的关系列在 `restored_relations` 里，带 `target_slug`。新卡已经用别的类型链接了那张卡时，这一行带 `linked_as`；目标卡被判为与某张已有卡相同（关系改为指向那张已有卡，并写在两张已有卡上），或在重试的合并核对里被并入另一张卡时，这一行带 `redirected_from`。其余带过来的关系仍留在 `skipped_relations` 里，原因是上面两种之一。

程序从不自动解决冲突：由你判断哪张卡对，改正另一张。任务结果在 `conflicts` 里列出冲突，`sb status` 在 `conflicts` 下列出所有未解决的冲突，`HOME.md` 在「现在做什么」下给出数量。已有卡片的正文改动之前，冲突一直列着；只给那张卡补上反向关系不算改动，补丁则会把那张卡未解决的冲突重新记一次。每处冲突按来源、卡片和已有卡片只算一次：重试子任务再次记下父任务记过的冲突时，显示的是重试的那条记录。

### 任务结果里列出什么

除了 `produced`、`pending`、`needs_taxonomy`、`out_of_scope`、`new_topics`、`conflicts` 和上面几张关系单，入库任务的结果里还有：

| 字段 | 内容 |
|---|---|
| `outcomes` | 每张接受的卡的结局：`write`、`patch`、`drop`、`merge_carry`、`merge` 或 `pending`；写在已有卡旁边的卡是 `write`，已有卡全都说过的卡是 `drop`，等你处理的卡是 `pending`。并进别的卡的每张卡，程序都把它的去处记进决定记录（`outcome.program`，附理由），`outcomes`、`patch_set`、`merge_set` 和 `pending` 都从这份记录读出，所以总是一致 |
| `decision_record` | 任务的每个值，附给出它的角色、槽位和运行 |
| `duplicates` | 已有卡片已经含有的卡和段落，附 `with` 和 `by`（`reviewer` 或 `producer`） |
| `merged_into_existing` | 接受了补丁的每张已有卡：补进它的卡、新命题的编号、被替换的命题与问答（`replaced`，以及带替换前后原文的 `replacements`）、新问答的组数、移过来的关系，以及合并核对的 `already` 行 |
| `replacements_not_made` | 因补丁或 `carry` 没有整份补进（进了拆槽）而没有换的问答：新问题与新答案，以及原因 |
| `split` | 写入的每张拆出的卡：它的 id、它从哪张卡来、它缩窄的已有卡和它的槽位 |
| `split_restated` | 因拆槽复核者把某条命题对上了已有卡、被程序退回的每张拆卡：槽位、第几轮和 `matches` |
| `patch_set` | 补充已有卡的每张卡，以及它的去向：`patched`、`split`、`covered`（已有卡全都说过）、`written`（写在已有卡旁边）或 `pending` |
| `merge_set` | 本来源里因为太大、不能并进本来源另一张卡的每张卡：`split` 或 `pending` |
| `source_check` | 合并核对在来源内部做了什么：`merged`（带 `carried` 计数，以及带替换前后原文的 `replacements`）、`added_links`、`alone`、`refiled_topics`、`moved_relations` 和 `rewritten_links`，或 `status: skipped` 加原因 |
| `source_check_refusals` | 程序退回的每份合并核对答案，附退回信息 |
| `needs_review` | 写在已有卡旁边（或 `carry` 被扣下时，写在本来源那张卡旁边）、标为待复核的卡，附 `with`、原因和 `not_merged` |
| `patches_held` | 在合并核对的最后一份答案里补丁没过检查的每张已有卡：补充它的卡和查出的问题；并进本来源某张卡的 `carry` 没过检查的卡（`carry: true`）；因补进后会超过 8 组而扣下的问答（`review_cards_only: true`） |
| `amended` | 每条机械修正，附改前和改后 |
| `program_repairs` | 程序对答案做的每处修复（不写知识文字），按槽位列：去掉的代码围栏或 JSON 对象前后的文字（`fence`、`around`，任何角色）、块与拆槽生产者用到的[检查之前程序先修什么](#检查之前程序先修什么)里的规则，以及槽位最后一份答案扣下的内容（`held_back`） |
| `review_notes`、`notes_turned` | 每条复核备注及其类别；程序改成退回的接受（[复核规则](#复核规则)） |
| `refused_topics` | 复核者退回的每个新主题，附理由和归在它下面的卡片数 |

## 待你处理的事

`sb status --owner-items` 把所有等你处理的事列在一张单上，每项带 `owner_reason`：

| `owner_reason` | 事项 |
|---|---|
| `source_unclear` | 来源不清、标为待复核的卡（记录原因之前就标为待复核的卡也算在这里） |
| `possible_repeat` | 写在它所补充的已有卡旁边、标为待复核的卡；那张卡为什么没接受它，写在 `detail` 里 |
| `conflict` | 与已有卡未解决的冲突 |
| `pending` | 部分写入的来源最新一个任务里的待定项；某篇文章最新一次导出里没通过复核的段落（`kind: export_paragraph`，见 [export.zh-CN.md](export.zh-CN.md)）；停下来等你处理的维护类任务（分类、整理、移卡、建领域），附任务、类型、停在哪一步和理由（`kind: maintenance_job`；每种操作只算最新的一个任务）；程序读答案、查答案时出的错，附任务、槽位、角色、哪一步、错误和次数（`kind: program_error`） |
| `needs_taxonomy` | 在分类体系里没有位置的段落（`kind: passage`），或复核者退回的新主题，附理由和卡片数（`kind: refused_topic`） |

这张单每次从知识库和任务记录现算，不另存任何东西。`sb status` 在 `owner_items` 下给出各项的数量。

`sb status` 还在 `topics` 下报告主题的大小：超过一页地图（25 张卡）的主题，每个附上整理它所在领域的 `sb curate --domain <slug>` 命令；分类体系里有、却没有卡片用的主题数；归在分类体系没列出的主题下的卡片数。对每个超过 25 张卡的主题，`sb curate` 会拿到一份提议，说明它的卡按彼此的关系可以怎样分组（`split_proposals`）。这只是提示：拆不拆仍由 `sb curate` 决定，卡片都不变。少于 5 张卡的组并进它链接最多的那一组，并不进去的列为零散；分完仍超过 25 张的组，标明还要分第二轮。这份提议需要 `curate` 可选依赖（`networkx`）。在一个大型知识库最大的 10 个主题上，一位独立的判官认为其中 9 个的分组合理。

## 任务保留的设置

任务冻结时，保留 `[review]` 规则（连同 `--max-rounds`）、`[ingest]` 设置、知识库的目录布局和卡片语言。它的各个步骤从任务里读这些设置，不读配置文件。所以改了配置文件，或换了 `--max-rounds`，不会让任务半途变规则。只有“怎样运行”的设置是现读的：端点和 key、宿主交接里写明的配置文件、git 提交、状态目录。

重试子任务沿用父任务的 `[ingest]` 设置，用当前的 `[review]` 规则。冻结时某项设置还不存在的任务，按冻结它的那个版本运行：候选卡用以前的张数（`candidates_k = "auto"`），复核包里没有点名卡，检索命中的卡用 `full`，没有书架，不补进已有卡，没有前文说明。

**上一版的任务**（任务输入里是 `method_version: ingest/3`）用另一把尺判重复，所以这一版不接着跑它：

- 部分完成的任务：运行 `sb ingest --retry <job>`。子任务是这一版的任务。它读父任务的记录，一直跑完，不会把父任务写过的卡再写一遍。
- 还在进行中的任务：`sb job advance` 会拒绝，并说明怎样出来。先用 `sb job reset <job> --reason "<why>"` 重置，再重新运行 `sb ingest <inbox path>`。上一版的重试子任务：先重置它，再运行 `sb ingest --retry <parent>`。

已完成的上一版任务，按它当时的规则读（一轮返修、整卡复核、没有机械修正），所以 `sb job show` 显示的是它当时做了什么。

## 任务与恢复

所有进度都存在任务里，位于知识库之外。中断之后，先运行 `sb job list` 和 `sb job show <job_id>`，再用 `sb job advance <job_id>` 继续。

```sh
sb job list
sb job show <job_id>
sb job advance <job_id> --executor host
sb recover <job_id> --rollback      # 逐字节还原这个任务写过的每个文件
sb recover <job_id> --resume        # 完成被打断的写入
sb job reset <job_id> --reason "<why>"   # 搁置一个卡住且从未写入的任务
sb job skip-source-check <job_id> --reason "<why>"   # 合并核对一再失败后，不经核对写入
sb job prune --days 30              # 预览旧的回滚日志；加 --apply 才删除
```

写入之前，事务把每个文件与计划时所依据的字节比对。如果期间有别的程序改了某个文件，任务停下，状态为 `needs_attention`；下一次 `sb job advance` 用同一批复核过的卡片重新规划写入。多份来源可以同时处理；对同一个知识库的写入在锁的保护下逐个进行。

回滚过的来源可以再次入库。回滚也会还原接受过补丁的已有卡。

`sb recover <job> --rollback` 要用任务的回滚日志（任务状态目录里的 `transaction.json`），工具从不自行删除它。`sb job prune` 预览可以删除的日志并给出大小：已完成、早于 `--days` 天（默认 30）、且不是其来源或操作最新一次写入的日志。同一来源的父任务和重试子任务算一个来源；其他任务按操作分组，例如 refresh 或 daily。`sb job prune --apply` 删除这些日志和它们的写入计划；这些写入从此不能撤销，写入的卡片保留。`sb status` 在 `state_dir` 下给出状态目录：总大小、每个顶层文件夹的大小（`parts`，例如 `jobs` 和 `cache`），以及 `sb job prune` 现在能释放多少（`prunable_mb`）。cache 里是解析缓存和检索索引，会随知识库增大，删掉后会重建。

`sb ingest --retry <job>` 把部分完成的任务里的待定卡作为子任务运行。子任务名为 `<job>-retry1`，依此类推，各有自己的事务。先回滚重试子任务，再回滚父任务：子任务写入的内容还在知识库里时，`sb recover <parent> --rollback` 会拒绝执行，并指出是哪个子任务。已回滚或已重置的子任务不妨碍新的 `sb ingest --retry <parent>`；新的子任务沿用它的 id。

重试子任务能看到这份来源以前的任务里没有做成卡片就已了结的内容（已有卡片已经含有的段落、超出范围的段落），不会再写一遍。它的结果里有 `retry_progress`：`open_before`、`open_after`、`cards_written` 和 `progress`。如果子任务一张卡也没写，留下的待定项与收到的一样多（`progress: false`），结果里给的是 `message` 而不是重试 `hint`：再重试多半还是这样。先读 `pending` 里的理由（`sb job show <job>`），改掉卡住它们的原因（例如新主题所需的分类体系）后再重试；或者让它们留着，用 `sb inbox skip <file> --reason "..."` 结束这份来源。`sb inbox list` 和 `sb ingest <source>` 也会这样提示。对已经重试过的任务再运行 `sb ingest --retry`，不会再开子任务：它返回一份简短摘要，`message` 指出这条链上最新的任务；那个任务是 `partial` 且有进展时，还附上重试它的 `hint`。

## 用于已有知识库的其他命令

这些命令对知识库里已有的卡片使用同样的生产、复核、闸门模式。

| 命令 | 作用 |
|---|---|
| `sb refresh` | 预览会变动的地图页；加 `--apply` 写入。知识库里已有别处来的地图页时，第一次 `--apply` 还会给每页加上 Breadcrumbs 字段 `BC-list-note-field: down`（[详见](new-vault.zh-CN.md#4-检查并生成地图页)） |
| `sb classify --domain <slug>` | 为没有支柱和主题的卡片提议支柱和主题（`--repair-invalid` 用于分类已不再合法的卡片） |
| `sb backlog` | 分批对整个领域或整个知识库做分类 |
| `sb curate --domain <slug>` | 提议修改已有领域的支柱和主题；超过 25 张卡的主题，它会拿到一份怎样拆分的提议（[见上](#待你处理的事)） |
| `sb relocate --source-job <job>` | 分类复核建议换领域时，把卡片移到另一个领域 |
| `sb domcreate --domain <slug> ...` | 根据已有卡片提议一个新领域 |
| `sb resume --job <job>` | 继续上述命令的某个任务 |
| `sb export --domain <slug>` | 把一张地图的卡片写成一篇文章（[export.zh-CN.md](export.zh-CN.md)） |
| `sb docs --apply` | 重新生成首页 `HOME.md`（以及 `[layout] entry_docs` 的生成块） |
| `sb today --apply` | 在 `50_Reviews/` 下写当前复习日的复习页：复习登记表里的到期卡和新卡，与这个复习日里 `sb review queue` 给出的队列相同。复习日从 04:00 开始，所以 01:00 生成的页仍属于前一天。它不改 `HOME.md`。需要 `review` 可选依赖（extra） |
| `sb daily --apply` | 两件事都做，`HOME.md` 会链接新生成的复习页；复习页缺失时，HOME 提示的就是这条命令。没装 `review` 可选依赖时只写 `HOME.md`，并报告 `review_extra_missing` |
